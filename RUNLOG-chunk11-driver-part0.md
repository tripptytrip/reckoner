# Part 0a — inventory of the existing compositions

`BRIEF-chunk11-driver.md` §0a. The driver **promotes** the tested composition, so
this names what exists, what it diverges from, and — the part that matters — what
the tested composition has **never exercised**, because that is built rather than
promoted.

## 1. There are two compositions, at different levels

### `scripts/golden.py` — the real loop, at golden config

End to end, per iteration:

```
training_problems(source, episodes, seed=n)     # frozen-instrument refusal in force
run_iteration(problems, uniform_stub(cfg), cfg, ring, sims=8, m=5, seed=n)
stats.check_descent_identity()
train_on_ring(model, ring, cfg, steps=2, seed=n)
consider_switch(head, labels, predictions, iteration=n)
    -> switch_event_row -> append_row(value_switch.jsonl, VALUE_SWITCH_FIELDS)
iteration_row(stats, ...) -> row
RunState(iteration=n, value_head=head, seed=n)
commit_iteration(run, ring, state, write_row)   # the four-step order
```

then, after the loop: `read_rows` → `alarm_census`, `resume(run, cfg)`,
`pool.enroll(...)` ×3 → `pool.composition()`.

**This is the composition.** It is what the driver must be, not what the driver
must be written beside.

### `tests/test_resume.py::Harness` — a commit-protocol probe, not a loop

Three iterations, each appending **two fabricated ring records** (`a_record`) and
writing a **fabricated row** (`{"iteration": n}`), with two kill points:

- **A** — ring and state on disk, row not yet written
- **B** — row written, `LATEST` not yet renamed

It runs no self-play, no training, and not the real row schema. Its synthetic
payloads are the point: they isolate the commit contract so the kill tests are
fast and cannot fail for a reason that is not the commit contract.

## 3. Two findings that change the brief's shape

### 3.1 The tested composition has never put the model in the search

`golden.py` runs `run_iteration(problems, uniform_stub(cfg), ...)`. **The model is
trained but never consulted.** `train_on_ring` moves the weights and golden
asserts that it does — but the episodes those weights are trained on were
generated by flat priors, every iteration, by construction.

So "promote the tested composition" promotes a loop in which the model→search→ring
feedback path — *the loop's entire subject* — has never run. That path is
`model_evaluator` in place of `uniform_stub`, and it is **built, not promoted**.

The same applies to pool par: golden calls `pool.enroll` and asserts
`composition()` grows, but never draws a problem whose par came from a snapshot.
`par_from_pool_frac` has no exercise in any composition.

This is not an argument against the one-composition ruling — it is an argument
that the ruling's Part 0 has surfaced exactly what it was meant to. Both gaps are
now design items with names, ahead of the code.

### 3.2 The kill-point tests should not be re-pointed wholesale

The brief's DONE-WHEN asks for both kill points through the driver, killed-and-
resumed identical row for row. Read literally against `Harness`, that would
replace fabricated payloads with real self-play and training — turning a fast
contract probe into a slow loop test, and coupling *"does `commit_iteration`
survive a kill at A"* to every reason a training iteration can fail.

**Proposed reading, for ruling:** the one-composition law binds the *loop* —
golden and the driver must not be two loops. The `Harness` is a level below it,
probing a seam the driver also uses. So:

- `Harness`'s synthetic kill-point tests **stay as they are**, fast and isolating.
- The driver **drives the same `commit_iteration` seam**, which is what makes
  them tests of the driver's commit path rather than of a parallel one.
- A **new** driver-level kill test is added at campaign-shaped-but-tiny config,
  asserting killed-and-resumed is row-for-row identical to uninterrupted — the
  DONE-WHEN's actual claim, proven on the real composition.

That satisfies "one composition" where the phrase bites — one loop — without
discarding a probe whose synthetic payloads are a feature.

## 4. What Part 0 concludes

The driver is `golden.py`'s loop with: config in place of flags, the model in
place of the stub, pool-sampled par, the anchor as the starting checkpoint, the
ladder pass on its cadence, the three additional row classes (funnel, no-regress,
pool composition), and the fingerprint assertion at startup. `golden` becomes that
driver invoked at golden config.

Two items in that list are new capability rather than promotion — §3.1 — and one
DONE-WHEN needs the reading in §3.2 before it can be met as written.
